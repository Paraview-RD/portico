# 备份与恢复

要备份什么、一份备份在缺了另一半时值多少、以及你真的用上它时会发生什么。

## 状态存储位置

| 在哪 | 是什么 | 怎么丢的 |
|---|---|---|
| PostgreSQL | 除下面那一行之外的全部：账号、组织、租户、设置、审计轨迹、会话，以及**每一把私钥**——OIDC 签名密钥和 SAML 证书都在表里 | 数据库被删、一次糟糕的迁移、一个被删掉的租户 |
| `PORTICO_JWT_SECRET` | 给 Portico 自己的会话令牌签名的那个密钥。**它不在数据库里，从来也没在过** | 重装的主机、被轮换掉的密钥管理器条目、丢失的 `.env` |
| `PORTICO_ENCRYPTION_KEY` | 目录 bind 密码所使用的加密密钥。同样不在数据库里，而且是刻意的：**导出里有密文，没有能打开它的东西** | 同样的那三种方式 |

**只有 `pg_dump` 的备份不是这个系统的备份。** 把它恢复到一个 `PORTICO_JWT_SECRET`
不同的实例上，一切都回来了——**除了每一个登录中的人都被立刻退出登录，包括你本来打算
用来检查恢复是否成功的那个管理员**。数据库完好无损，而部署看起来是坏的。

这不是预测。恢复一份导出、用一个新密钥启动，数据是对的——密码仍然有效，`/ready` 回
200——**而每一个此前签发的令牌都回 401**。日志里没有任何一行写着"密钥不对"；它读起来
就像一个无缘无故把所有人踢出去的实例。

**只有导出加 JWT 密钥，如果你从目录同步，也一样不够。** `PORTICO_ENCRYPTION_KEY`
是 LDAP bind 密码的加密密钥，而那是本系统中**唯一一个必须可还原、而不是只需可校验**的
凭据——Portico 每次执行都要把它发给你的目录。用一个不同的密钥恢复，**每一个目录连接器
都会在 bind 这一步失败**，而报出来的是目录那边关于凭据的错误，没有任何一处提到这个
密钥。每一个数据源的 bind 密码都得重新输一遍，而且**没有办法从导出里把旧的还原出来**。

**用和数据库同样的谨慎、同样的周期去备份这两个密钥，并让三者可以被一起恢复。** 它们是
一份备份，分在三个文件里。

## 数据库导出里含有私钥

`oauth_signing_keys.private_key` 和 `saml_signing_keys.private_key` 是 PKCS#8 PEM，
以**明文**存储——这是一个刻意的决定，与它们旁边的密码哈希处在同一档：**保护数据库是
部署方的职责。**

`webhook_subscriptions.secret` 就在它们旁边，同样是明文，而理由值得写出来而不是让人
去猜：**它和客户端 secret 或 SCIM 令牌不同，从不用于和调用方出示的东西作比对**。它是
用来**产生**每一次投递上那个签名的，所以没有什么可哈希的，存摘要也没有用。**拿到一份
导出的人，可以签出一次让每一个订阅方都验证为真的投递。**

但它对备份的后果**不是刻意的，除非你把它变成刻意的**。一份躺在对象存储里、使用默认
权限的导出，就是**你的身份提供方的签名私钥躺在对象存储里**。拿到它的人可以签发你的
依赖方会接受的令牌、以及你的服务提供方会信任的断言，而且可以一直这么做下去，**直到
每一把密钥都被轮换、每一个服务提供方都被通知到为止**。

**不**在明文之列的是目录 bind 密码：那一个用 AES-256-GCM 加密，密钥
`PORTICO_ENCRYPTION_KEY` 在环境变量里而不是数据库里，所以**单有一份导出拿不到它**。
这是上面那个拆分唯一真正买到东西的地方。

每一份这样的值还会与"它是什么、属于谁"一起封存，所以把一段密文从一行挪到另一行——把某个
webhook 的请求头挪进某个目录的 bind 密码、把一个租户的凭证挪进另一个租户的行——都不再能
解开。**因此把备份恢复到另一个租户下时，这些凭证不会跟着过去**：行会恢复，但封存的值打不开，
必须重新填写。在这个机制之前写入的值仍然可以打开，并会在下一次保存时按所在行重新封存。

对静态导出加密、限制谁能读它，并且**把一次泄露的备份当作密钥泄露而不是数据泄露来
处置**——两者的应对不一样，前者要大得多。

## 做一次备份

```bash
pg_dump --format=custom --file=portico-$(date +%F).dump "$PORTICO_DB_DSN"
```

用 `--format=custom` 而不是纯 SQL：它会压缩，而且能用 `pg_restore` 恢复，那样可以让
它在遇到已存在的对象时继续下去，而不是**在数据库写了一半的时候中途失败**。

**让客户端与服务端版本对上。** `pg_dump` 会拒绝从比它自己新的服务端导出，而更糟的
是——一个旧客户端对着新服务端，**可能产出一份能恢复、但内容有缺失的导出，而不是报
一个错**。两边都查一下：

```bash
pg_dump --version
psql "$PORTICO_DB_DSN" -c 'SHOW server_version'
```

如果主版本不一致，就用与服务端同版本的容器来跑 `pg_dump`，而不是用主机上装的那个。

密钥只有一行，它属于你其它密钥所在的地方：

```bash
# 对你来说这是什么就用什么：密钥管理器、加密文件、vault。
echo "$PORTICO_JWT_SECRET" | your-secret-store put portico/jwt-secret
```

## 恢复

在实例停止的状态下，恢复到一个空数据库：

```bash
createdb portico_restored
pg_restore --dbname=portico_restored --no-owner portico-2026-08-08.dump
```

然后**用导出当时正在使用的那个 `PORTICO_JWT_SECRET` 和 `PORTICO_ENCRYPTION_KEY`**
启动 Portico。把
`PORTICO_DB_DSN` 指向恢复出来的数据库然后让它启动即可：**迁移是内嵌的、在启动时执行**，
所以一份来自旧版本的导出会被自动带到当前版本。没有一个需要记住的单独迁移步骤，也没有
工具需要安装。

**检查恢复结果时，要用一个会读数据库的东西，而不是一个只读进程的东西**：

```bash
curl -sf http://127.0.0.1:8410/api/v1/ready     # 200 表示数据库应答了
```

`/health` **不是**这个检查。它刻意不碰数据库，所以对一个数据库根本连不上的已恢复实例，
它照样回 200——见 [访问指南](access-guide.md)。

## 时间点恢复的注意事项

这些都是数据本身的含义带来的后果，**而且没有一件会自己声张**。

**吊销被撤销了。** 退出登录、改密码、停用账号，全都是通过写数据库实现的——账号上的
`token_version`、会话行上的一个吊销标记、刷新令牌（refresh token）链上的一个吊销标记。恢复到一
次吊销**之前**的时间点，就是恢复到"那个凭据仍然有效"的状态。**一个因为泄露而被吊销
的令牌会重新开始工作**，直到它自己的有效期走完为止。

如果你**正是因为**一次入侵而恢复，就把轮换 `PORTICO_JWT_SECRET` 作为恢复的一部分。
那会一次性作废所有会话令牌，无论恢复出来的行里怎么写，代价是把所有人都退出登录——
**而事故期间这本来就是你想要的**。轮换覆盖不到刷新令牌；对那些改为停用受影响
的客户端。

**SAML 服务提供方可能不再信任你。** 依赖方会自己去重新拉取 OIDC 密钥集，所以恢复一
把旧的签名密钥对它是不可见的。**SAML 服务提供方不会**：证书被钉在它的配置里，只有
人去告诉它，它才会知道有了新的。如果证书是在导出之后轮换的，那么这次恢复会把服务提
供方**已经被配置为不再使用**的那把密钥放回来，于是**每一次登录该应用都会在签名校验
上失败，而且没有任何一条消息指向真正的原因**。在认为恢复已经完成之前，拿
`saml_signing_keys` 和你的服务提供方手上持有的东西对一下。

**审计轨迹现在比事情本身短。** 导出之后写入的条目没有了，**而轨迹不会记录自己被截断
这件事**。如果被覆盖掉的那段时间要紧——**而在事故期间，那通常恰恰就是要紧的那一段**
——那就在替换掉受损数据库**之前**，先把它的审计条目导出来，哪怕它在别的方面已经不
可用了。

## 演练

**一份没有人恢复过的备份是一个文件，不是备份。** 上面那些失败模式全都是无声的，所以
唯一确认的办法就是真的做一遍：

1. 把昨晚的导出恢复到一个临时数据库。
2. 用归档的那个密钥、在另一个端口上，对着它启动一个实例。
3. 用一个**普通账号**登录——不要只用管理员，那个密码你可能是用环境变量设的，因此它
   证明的东西比看上去少。
4. 如果你有联邦应用，端到端验一个还能不能用。

**第四步正是能抓到 SAML 证书问题的那一步，也正是会被跳过的那一步。**

## 升级

启动时只跑 `goose.Up`，别的什么都不跑，所以迁移**永远只向前**。向下的迁移确实存在，
而在你伸手去够它之前值得先知道它是什么：**它会删掉每一张表**。它是用来重置开发数据
库的，不是用来把一个部署退回上一个版本的——**跑它和删数据没有区别**。

所以**不存在降级路径**，而这是模式变更本身的性质，不是一个疏漏：一次已经删掉某列的
变更，无法把它的内容再发明回来。**升级前先做一次导出。** 回退一个版本意味着恢复那份
导出，而不是拿旧的二进制去对着新的模式跑。

容器镜像不带任何状态——`PORTICO_ADDR` 加一个数据库就是全部——所以升级就是换一个新镜
像再重启。没有卷需要迁移，主机上也没有东西需要保留。
