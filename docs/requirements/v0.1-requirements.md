# Portico V0.1 需求文档（含 V0.2–V0.4 迭代路线图）

## 1. 文档说明

### 1.1 编写目的

本文档定义标准化身份认证平台**V0.1 最小可行上线版本**，聚焦「可生产上线、可对外标准化对接」的核心底座能力。仅纳入本次确认的刚需核心功能，所有高阶能力、复杂能力统一放入 V0.2～V0.4 迭代路线图，不参与首期开发。

本版本从原有轻量化内网IAM升级为**标准化、多租户、内外网通用身份底座**，补齐标准协议、多租户、多登录方式、自服务闭环、基础国际化核心能力，满足业务单点登录、下游用户同步、公网用户接入、企业基础隔离管控。

### 1.2 版本定位与边界原则

*   **V0.1 定位**：标准化身份平台基础底座，可对接标准业务系统、可公网部署、支持多租户隔离。
    
*   **迭代原则**：首期只做「必须上线、必须替换、必须兼容」的刚需能力，所有增强、扩展、高级集成能力分期迭代。
    
*   **架构原则**：一期架构打底，后续版本平滑叠加，不推翻、不重构。
    

### 1.3 适用范围

适用于内外网统一身份认证、公网用户自助注册/登录、标准化SSO单点接入、多租户数据隔离、基础组织人员管理、下游业务系统用户数据同步场景。

## 2. V0.1 能力总览（本期正式落地）

### 2.1 本期新增核心刚需（本次重点补齐）

*   支持四大标准SSO协议：OAuth2.1 / OIDC / SAML / CAS
    
*   全表字段级多租户隔离，基于 tenant\_id 实现数据隔离
    
*   内置中英文双语多语言支持（固定语言包，不含动态上传）
    
*   多维度账号登录：用户名 / 手机号 / 邮箱 三种登录方式
    
*   用户自服务闭环：支持找回密码、自助改密、个人信息管理
    

### 2.2 原有保留能力（延续上期基线）

*   内外网用户自主注册、Excel批量导入用户
    
*   标准化JWT Token鉴权体系，携带用户、角色、组织信息
    
*   极简组织管理（单根组织、用户单组织归属）
    
*   下游业务系统按需拉取用户/组织数据同步机制
    
*   极简权限体系：仅超级管理员 / 普通用户 固定双角色
    
*   基础登录、操作、注册、组织变更日志审计
    
*   系统基础配置、注册开关、Token时效配置

> * **会话管理**：每次登录单独成行，可分别查看与结束。
> * **Webhook 事件订阅**：用户创建/更新/启停等事件出站推送，HMAC-SHA256 签名
>   （时间戳纳入签名以防重放）、指数退避重试、投递记录可查。**SSRF 防护不可配置**：
>   仅 https、拒绝内网/回环/链路本地（云元数据）/CGNAT，且在**建立连接时**再校验一次
>   解析后的地址（防 DNS rebinding），不跟随重定向。
> * **SCIM 2.0 供给**：Users 已实现（含 externalId 对账、PATCH、停用即断访问），
>   凭据在控制台签发。**Groups 已实现**——新增独立的「用户组」概念（多对多），
>   与「组织」并存互不影响：组织是组织架构（单归属/树/有 code/下游同步），组是
>   人员集合（多对多/扁平/通常由目录维护）。硬把组映射到组织会破坏单归属或静默
>   改掉别人的组织，故不这么做。组成员身份不授予任何权限。

## 3. 核心功能详细需求（V0.1）

### 3.1 多租户管理（V0.1 核心架构能力）

平台底层全量数据表植入 **tenant\_id** 租户字段，实现字段级数据隔离，支撑多租户独立使用、数据互不穿透。

*   所有业务数据表：用户、组织、角色、日志、授权记录、配置数据全部携带租户ID
    
*   租户数据严格隔离，跨租户无法查询、修改、越权访问
    
*   支持单租户/多租户部署模式兼容
    
*   V0.1 仅底层隔离能力，租户管理后台运营能力迭代至后续版本
    

### 3.2 标准化SSO协议模块（四大标准协议）

对标标准身份平台，完整兼容主流标准化单点协议，支撑存量业务系统平滑迁移。

*   **OAuth2.1**：支持标准授权码模式，兼容主流第三方业务系统接入
    
*   **OIDC 1.0**：兼容标准IdToken、用户信息回传，标准化身份鉴权
    
*   **SAML 2.0**：支持SAML断言登录、企业级系统对接
    
*   **CAS**：支持CAS单点登录、统一登出逻辑
    

协议能力约束：V0.1 完成标准协议基础对接能力，精细化应用配置、字段映射、高级授权策略迭代至后续版本。

### 3.3 多语言管理（内置中英双语）

*   系统全局内置 **简体中文、英文** 两套固定语言包
    
*   前端支持语言快速切换，覆盖登录页、自服务页、后台管理页、提示文案
    
*   V0.1 不支持后台动态上传语言包，该能力纳入 V0.4
    

### 3.4 登录模块（多账号体系登录）

支持三种账号体系独立登录，满足不同用户场景接入。

*   用户名密码登录
    
*   手机号密码登录
    
*   邮箱密码登录
    

统一登录校验、会话管控、JWT签发逻辑，三种登录方式生成身份凭证完全一致。

### 3.5 用户自服务模块（V0.1 完整闭环）

面向终端用户提供自助管理能力，无需管理员介入。

*   自主注册账号（后台可开关注册功能）
    
*   自主修改登录密码
    
*   **找回密码**（通过绑定邮箱/手机号完成校验重置）
    
*   个人基础信息查看与维护
    

### 3.6 用户管理模块

*   用户新增、编辑、启用/禁用、状态管理
    
*   Excel批量导入用户、适配存量迁移
    
*   用户绑定所属组织、后台可迁移用户组织
    
*   自主注册用户默认普通用户、无后台权限
    

### 3.7 极简组织管理

*   一级组织创建、编辑、启停管理
    
*   用户单组织归属机制
    
*   组织变更日志记录
    

复杂多根组织、多组织挂靠、组织负责人能力迭代至 V0.2。

> **实现说明**：组织层级已在 V0.1 内追加实现（见 §2.3）。仍延后的是「一人
> 多组织」与「组织负责人体系」。


### 3.8 JWT Token 鉴权体系（含适用场景）

自研标准化JWT作为全局统一身份凭证，支撑内外网、单点、下游同步全流程。

#### 3.8.1 JWT 适用场景

*   内外网统一身份凭证，替代传统Session，支持公网跨域访问
    
*   四大标准协议单点登录身份载体，支撑标准化授权对接
    
*   下游业务系统单点身份识别、用户与组织信息同步唯一凭证
    
*   全局接口统一鉴权、身份合法性校验
    

#### 3.8.2 JWT 载荷内容

包含：用户ID、账号、昵称、角色身份、租户ID、组织ID、组织名称

#### 3.8.3 JWT 能力边界

V0.1 为自研私有标准化Token，服务自身与下游同步；标准协议对外授权字段由协议模块独立兼容。

### 3.9 下游用户数据同步机制（轻量化按需同步）

延续MVP轻量化方案：**下游业务系统单点访问按需拉取**，不做主动推送。

*   下游无用户则自动创建、已有用户则增量更新
    
*   同步字段：账号、昵称、手机号、邮箱、状态、租户ID、组织信息
    
*   IAM为唯一数据来源，保证单点场景用户信息、组织、租户信息一致
    

### 3.10 极简权限体系（固定双角色）

V0.1 不实现RBAC，仅固定两类角色

*   **超级管理员**：全功能管理权限，用户、组织、配置、日志、协议配置权限
    
*   **普通用户**：仅个人自服务、业务系统访问权限，无后台运维权限
    

### 3.11 基础日志审计

V0.1 覆盖基础运维审计，完整服务级审计迭代至V0.4

*   登录/登出日志、注册日志、密码变更日志
    
*   用户新增、状态变更、组织变更操作日志
    
*   Token鉴权、单点授权访问日志
    

## 4. 版本迭代路线图（V0.2～V0.4）

所有未纳入V0.1的功能，统一分期迭代，平稳叠加、不重构架构。

### 4.1 V0.2 迭代主题：目录对接 & 用户生命周期闭环

**核心定位：账号能从外部目录进来，也能由用户自己退出**

> **范围调整说明（成文于本文档之后）**：立项时 V0.2 的主题是「用户体系 &
> 组织架构增强」。其中两项在 V0.1 期间已经交付、或已明确改由其它方式解决，
> 见下方「移出」。腾出的位置给了三项新需求，主题随之改名——账号**从哪来**
> 和**怎么走**是同一条生命周期的两端，放在一期里做，共用同一套对账与审计。
>
> **第二次订正（成文于本期交付之后）**：实际交付的不止那三项。另有四项产品能力
> 做完了而路线图从未提过——应用图标、Webhook secret 轮换、Webhook 自定义头、
> 说明面板开关——现记入下方「本期另外交付」。**一份不记录已交付内容的路线图，
> 会让下一期把同一件事再排一遍。**

#### 实现前先定的一件事：账号状态怎么表达

B 需要「已注册但还不能登录」，C 需要「本人注销」与「管理员停用」可区分。两者都
在推 `model.Status`，而它目前只有 `ACTIVE | DISABLED` 两个值。

**决定：不动 `Status`，在 `users` 上加两个可空时间戳。**

- `verified_at`：联系方式已验证的时刻。空 = 未验证。
- `closed_at`：本人注销的时刻。空 = 未注销。

理由有两条。其一，`Status` 是**共用**的——组织和三类应用注册都用它，而它们
既没有「待验证」也没有「已注销」的概念；为一个实体的生命周期去撑宽一个共享枚举，
正是枚举腐化的起点，且 `INVALID_STATUS` 的文案（「只能是正常或已停用」）会连带
变成谎话。其二，这两件事本来就是「**什么时候发生的**」，那是时间戳不是状态。

登录判定随之变成：`status = DISABLED` 拒；`source = REGISTRATION 且
verified_at 为空` 拒（管理员建的、导入的、目录同步的账号不适用——它们由人或目录
背书，不需要邮件验证）；`closed_at 非空` 拒。

#### 本期新增（三项）

**A. AD / LDAP 作为数据源** ✅ **已交付**（用法见 [ldap.md](../ldap.md)）

这是与现有 SCIM **方向相反**的一条链路，必须先说清楚：V0.1 的 SCIM 是
**被调用方**——Portico 在 `/scim/v2` 提供服务端点，由目录（Okta / Entra ID）
主动推进来，Portico 从不主动去外部系统取数。LDAP 作为数据源是 **Portico 主动
拉**：连 AD / OpenLDAP，按过滤器读用户与组，落成本地账号。

- 连接配置：地址、Bind DN 与凭据、Base DN、用户/组过滤器、属性映射
  （`sAMAccountName`/`uid` → 用户名，`mail` → 邮箱，`displayName` → 显示名）
- 对账键沿用 SCIM 那套：`externalId` 存目录侧的稳定标识（AD 用 `objectGUID`），
  **改名是改名，不是第二个账号**
- 同步方式：手动触发，或按每个目录配置的间隔自动执行（15 分钟到 7 天，默认关闭）。
  **「增量优先」在实现中被推翻**——判断「谁从目录里消失了」必须枚举全量，增量查询
  看不到删除，半实现的增量会让停用逻辑静默失效。所以每次运行都是全量，这也是间隔
  有下限的原因。调度器跑在服务进程内，**不是**外部 cron 调
  `POST /api/v1/directories/{id}/sync`——那条路要访问令牌，等于把管理员密码放进
  cron 环境，比它要保护的 bind 密码更糟。多实例下靠一条原子领取语句保证同一目录
  一个间隔内只被枚举一次
- 目录中消失的账号**停用而不删除**，与 SCIM 的 DELETE 语义保持一致
- 同步记录可查：每次执行的起止、新增/更新/停用条数、失败明细
- **实现中追加的两条护栏**（原需求没写，但缺了它们这个功能是危险的）：目录返回
  空结果时拒绝执行并报错——Base DN 或过滤器打错，与「所有人都离职了」在协议层
  无法区分，照做会把该目录的账号全部停用；以及同步永不触碰不属于该目录的账号，
  归属是记录下来的而非按用户名推断，所以与目录里同名的管理员不会被改名或停用
- **不含 LDAP 认证**（拿 AD 口令直接登录）：那是联邦不是同步，与 V0.3 的
  第三方 IdP 登录是同一件事，放在一起做

**B. 用户自注册闭环** ✅ **已交付（验证部分）**

自注册本身 V0.1 已实现（按租户开关、默认关闭、固定 USER 角色、注册时不可
申请角色）。本期补的是「能开给外部用」所缺的那部分：

- **邮箱 / 手机号验证**：当前注册即为正常状态，填的邮箱不验证。而邮箱既是
  登录标识又是找回密码的收件地址，未验证就启用，等于允许拿别人的地址开户
- ~~注册项可配置：哪些字段必填、是否需要邀请码~~ → **未做，移出本期**
- ~~可选的管理员审核态：注册后待审，通过才可登录~~ → **未做，移出本期**

> **拆分理由**：这两条与验证不是同一件事。验证补的是「自注册**已有**的缺口」
> ——注册即启用、地址不核实；邀请码和人工审核是**新增的准入控制**，属于
> 「谁被允许注册」，不属于「注册是否闭环」。前者不做就不能对外开放，后者
> 不做只是少了两种收紧手段。放在一起做会让一个安全修复被两个产品选项拖住。
- 与目录同步的边界：LDAP / SCIM 管辖的账号不允许被自注册覆盖
  → **核实后确认：这条已由既有约束满足，不需要新代码。** 用户名在租户内唯一，
  所以自注册撞上目录账号的用户名会被 `USERNAME_TAKEN` 挡住；反方向（目录同步
  撞上自注册账号）在 A 里已实现为「跳过、计入 skipped、绝不接管」，并有测试。
  另外验证门只对 `source = REGISTRATION` 生效，目录账号不受影响，也有测试。

> **验证与邮件配置的关系，先定死**：验证是**按租户的开关**，不是硬性前置。
> 打开「需要验证」而本部署没配 SMTP 时，**保存设置这一步就拒绝并说明原因**，
> 而不是接受设置、然后让每个注册的人都卡在收不到的邮件上。这与首页那条
> 「联系方式提醒仅在该找回通道确实可用时才出现」是同一条原则：不要承诺一个
> 不存在的能力。

**C. 账号注销（用户自助）** ✅ **已交付（停用式）**

V0.1 没有这条路径，且它与两条既有决策相撞，**需要先定语义再动手**：

- 现状一：账号只停用、从不删除——为的是审计链路始终指向一个仍然存在的对象
- 现状二：`CANNOT_DISABLE_SELF` 禁止停用自己的账号——防的是管理员把自己关在门外

所以注销要做成**唯一一个允许自我停用的入口**，而不是放开上述限制。两种语义
各有代价，需产品拍板：

| | 停用式注销 | 删除式注销（匿名化） |
|---|---|---|
| 账号记录 | 保留，状态标记为已注销 | 删除，或改写为不可回指的占位 |
| 审计链路 | 完整 | 事件保留，行为人退化为匿名标识 |
| 同名重新注册 | 不可（用户名仍被占用） | 可 |
| 个人信息删除诉求 | 不满足 | 满足 |

无论选哪种，共同部分是：本人确认（重新输入密码）、注销后立即吊销全部会话与
下游 refresh token、审计留痕、下游经 Webhook 收到通知、**最后一名在用管理员
不可注销**（沿用现有 `LAST_ADMIN` 约束）。

> **实现取的是「停用式」**，并把这条写在这里而不是只写在提交信息里。理由是
> 可逆：它与「账号只停用不删除」这条既有决策一致，误操作可由管理员恢复，而
> 匿名化删除做错了没有退路。**匿名化删除仍然是产品的决定，不是工程的决定**
> ——它取决于你面对的是不是有个人信息删除诉求的场景。要改成删除式，
> `closed_at` 这套结构不必推倒，补一条匿名化的迁移即可。

##### 动手前先定的三件事

**① 30+ 属性取自 SCIM 2.0 核心模式（RFC 7643），不自创。**

Portico 本来就是 SCIM 服务端，属性名照抄标准有三个好处：目录推过来的字段能直接落位、
校验规则跟着标准走、以后加别的目录不用再谈一次字段含义。取 core User 的姓名分段、
昵称/头像/主页、职务/用户类型/语言/区域/时区、地址六段，加 enterprise 扩展的
工号/成本中心/部门/直属上级。

**不取** `organization` 和 `division` 两个自由文本字段——本系统已经有组织树，
再放一份手填的字符串必然与树漂移，而两份说法不一致时没人知道该信哪个。

**落成 `users` 表的列，不做 key/value 属性表。** 这是一组**固定的、来自标准的**
字段，列能被数据库校验、能建索引、能被 sqlc 生成类型。key/value 表是给
「租户自定义属性」准备的，那是另一件事，本期不做——两者事后不可互换，所以现在说清。

**② 一人多组织：改的是一条写在文档里的既有约定，必须明说。**

README、[scim.md](../scim.md)、[access-guide.md](../access-guide.md) 三处都写着
「组织：每人**恰好一个**」，并以此与「用户组：任意多个」区分。这不是随手写的，
是当初刻意的设计。

**做法：主归属 + 附加挂靠。**

- `users.organization_id` **仍然是唯一权威归属**——SCIM 与 LDAP 同步写它、导出报表
  按它、树上的位置是它。下游系统看到的组织不变。
- 新增 `user_organization_attachments`：**附加挂靠**，多对多，用于「研发部的人同时挂在
  某项目组」这种情况。**不授予任何权限**，不参与同步，不改变主归属。

这样三份文档里那张表仍然成立，只需补一行「附加挂靠：任意多个（不影响主归属）」。
如果哪天决定让附加挂靠也参与同步，那就是把组织合并成用户组了，届时要重新论证。

**③ 多根组织：核实后确认，已经支持，不需要写代码。** `parent_id` 为空即根，
表上没有唯一约束，服务层也没有「只能有一个根」的判断。属于「原需求写了、实现早已满足」
的一条。

买到的是**辨识度**:在门户上找应用，认图标远快于读完六个名字。

**E. Webhook secret 轮换** ✅ **已交付**

在此之前,secret 泄露的唯一补救是删掉订阅重建——**而那会换掉投递历史挂靠的 id、
以及接收方去重所用的 id,等于用毁掉证据的方式治病**。现在订阅保持 id 不变，被替换
的那把密钥再存活 24 小时。

**重叠期内每一次投递携带两个签名**，逗号分隔，任一验证通过即可。这不是实现细节而是
机制本身:签名由 Portico 产生、由接收方校验，**有东西要部署的是接收方**；立即生效的
轮换会在他们部署完之前拒掉每一次投递。

> **这条对每一个接收方都提出了要求。** 把 `X-Portico-Signature` 当作单个字符串比较
> 的接收方，在有人轮换之前一直工作正常，轮换之后开始拒绝一切、而自身看起来是健康的。
> [webhooks.md](../webhooks.md) 的示例代码已按 `,` 切分。

**F. Webhook 自定义头** ✅ **已交付**

给网关后面的接收方用——它想要一个自己的 `Authorization`。签名说明**是谁产生了这个
请求体**，而网关要判的是**这个请求该不该被放进来**，签名回答不了后者。

头的值用 `PORTICO_ENCRYPTION_KEY` 封装，与目录 bind 密码同一档；**没配密钥时保存被
拒绝**，而不是明文写下去。值从不回传,API 与控制台只报名字，这样列表不会变成读取
租户全部凭据的入口。会改变投递**本身是什么**的头(签名头、`Content-Type`、`Host`
等)在注册时就被拒。

**G. 说明面板可按租户关闭** ✅ **已交付**

给已经熟悉产品、每天读同样四句话的运维。默认开启——**看不懂一个界面的代价，大于
看到一句已经不需要的解释的代价**。单个面板仍可各自折叠，那是记在浏览器上的，所以
一个人收起面板不等于替所有人做了决定。

**H. 引导管理员改用默认密码 + 首次登录强制改密** ✅ **已交付**

在此之前，不设 `PORTICO_INITIAL_ADMIN_PASSWORD` 就会生成一个随机密码、只往 stderr
打一次。它只在"那行字还在"的前提下更安全，而**这个前提经常不成立**——终端滚过去
了，或者容器日志被丢了。丢了就没有受支持的回路:这个账号没有邮箱也没有手机号，
找回没有通道，也没有 `portico user` 子命令。

现在默认密码是文档里写明的 `Portico@1`，而**没换掉之前登录直接被拒**——返回
`PASSWORD_CHANGE_REQUIRED`，不发令牌。这一点是"能公开一个默认密码"的全部前提:
不是发一个令牌再带个标志位让客户端自觉，那种约定 API 客户端根本不会遵守。走的是
密码过期本来就有的那条路(`POST /auth/password/expired`)，它收旧密码与新密码、
自己签发会话。

> **它留下的窗口是真实的。** 从首次启动到首次登录之间，任何够得到这个端口的人都能
> 用手册里的密码把这个账号占了——占了之后设的密码你不知道。启动横幅因此写的是
> "现在就登录"，而不是"登录后改掉"。设了 `PORTICO_INITIAL_ADMIN_PASSWORD` 就完全
> 不适用:自己选的密码不在任何手册里，也不会被强制更换。

##### 另外两件不算产品需求、但改变了这个项目怎么工作的事

**开发数据种子(`cmd/seed`)。** 空库的 Portico 没法看:每个界面都是空状态，用户列表
分不出页，而「这个目录什么时候开始不工作的」「哪一条投递卡住了」这些**产品存在的
理由**没有过去可供回答。现在一条命令生成两个租户、五十五个账号、三种协议的应用、
两个方向的目录对接，以及九十天的历史。

**文档与代码的一致性改由测试强制。** 一次审计查出 37 条「文档说的和代码做的不一致」,
逐条修完之后加了八道机器校验:包与命令清单、Go 版本、三协议属性名、SCIM schema、
openapi 的响应 schema 与请求体、「解析租户的端点必须声明 404/403」，以及「所有示例
DSN 用同一个端口」。**它们查的不是散文，是名字、数字和状态码**——也就是审计里 37
条问题全部所在的那个盲区。

#### 新增：多因子认证（MFA）

**范围先定死三条：**

- **做 TOTP**（RFC 6238，任意验证器 App）。只要一个共享密钥和时钟，离线可用，
  不引入任何外部服务依赖——与本项目「除数据库和邮件中继外不外挂东西」的取向一致。
- **不做短信验证码。** NIST SP 800-63B 已将短信 OTP 降级（SIM 交换与 SS7 拦截
  是现实攻击面），且本项目至今没有任何一个 SMS provider 实现——用一条自己都发不
  出去的通道充当第二因子，只是把「支持 MFA」写进功能表。
- **不做 WebAuthn / Passkey / 推送确认。** 它们更强，但要引入新的前端与凭据模型，
  与本期「打通应用生态」不在一条线上。留待更后面，且届时是新增而非替换。

##### 动手前要定的几件事（**尚未定**）

以下只记问题与选项，**不记结论**——本期尚未开工，此处若写成定论，就会变成上面
那两条已交付却仍挂在路线图上的东西的镜像：一段没人复核过、却被后来者当作依据的
文字。定了之后再照 §4.1 的样子改写成决策。

**① 最后一个管理员被自己的第二因子锁在门外——现有的三道护栏一道都拦不住。**

这是本期唯一一条会**新开一个洞**的需求，所以放在最前。系统里已有三处不让租户
失去最后一个管理员：批量停用、自己停用自己、本人注销。三处走同一个判据
`CountOtherActiveAdmins(role, status, excludeUserID)`——**按状态数人**。而一个丢了
手机的管理员，账号是 `ACTIVE`、密码正确，只是交不出第二因子；三道护栏全都把他
数在内，于是全都不触发。单管理员租户 + 已启用 MFA + 手机丢失 = 租户永久锁死，
命令行也救不了：`portico` 目前只有 tenant / client / sp / cas / ready，没有任何
针对某个用户的子命令。

三条出路，动手前选一条：

1. **恢复码是启用流程的一部分**——一次性显示、只存哈希、用掉即失效，且最后一个
   管理员必须确认已保存才允许启用。
2. **加一条命令行逃生口**（如 `portico user reset-mfa`）。代价是能登上服务器就
   等于绕过第二因子——但能登上服务器的人本来也能直接改数据库。
3. **不允许最后一个管理员启用 MFA**。最简单，也最讽刺：最该有第二因子的账号没有。

**② MFA 失败要不要计入账号锁定计数。** 不计入，第二因子就是一个可无限爆破的
六位数；计入，则任何知道用户名和密码的人都能把人锁死——但那个前提本身已经意味着
密码泄露了。两害相权，需要一个明确的选择而不是默认行为。

**③ 启用 / 重置 / 关闭 MFA 要不要终止现有会话。** 这三件事都是凭据变更，与改密码
同类，现有的 `token_version` 自增一步即可复用。不终止，攻击者已持有的会话不受新
因子影响。

**④ 协议侧要不要如实上报 `amr` / `acr`。** 不报，下游应用无法区分「密码登录」与
「密码 + TOTP 登录」，也就无法对高风险操作要求强认证——MFA 只保护了 Portico 自己。

**⑤ TOTP 密钥属于要「使用」而非「校验」的凭据**，与目录连接器的 bind password
同类，直接复用 V0.2 建立的 `PORTICO_ENCRYPTION_KEY` 与 `internal/secrets`
（AES-256-GCM）。那套东西当初就是按「不止一处会用」设计的——**第二个使用者已经出现
了**（V0.2 的 webhook 自定义头，见 §4.1 F），本条会是第三个。

**⑥ 强制策略按租户**：关闭 / 仅管理员必须 / 全员必须。第三档打开的瞬间，所有存量
账号会在下次登录时被要求注册因子——这是一次面向全租户的中断，开关处必须说清，
参照 V0.2 中「打开注册验证不影响已注册的人」那条的处理方式。

#### 「管理员权限细粒度管控」是什么——一个解读，写下来是为了便于推翻

原文只有这半句，两种读法的工作量差一个数量级。在此写下解读，是为了让产品负责人
**能够推翻它**，而不是让它在动手那天由实现者随手定义。

**解读：指控制台内部的自定义角色与权限点**——谁能进哪个后台功能、能在其中做哪些
动作。依据有二：其一，V0.1 明确延后的是「自定义角色和权限」，本条是它的下文；
其二，Portico 是身份提供方，交给下游的是身份断言，业务系统自己的资源该不该放行
由它们自己判定。

**因此不包括对外的策略引擎（PDP）**——不替业务系统判定它们的资源。那是另一个
产品形态，真要做是重新立项，不是一个迭代条目。

**两条的次序不能颠倒**：权限点是判定，菜单可见性是它的投影。先做可见性、把菜单
藏起来，藏起来的菜单不是权限——地址栏里敲进去照样能用。V0.1 已经是这个次序
（普通用户只看得到两个入口，但边界在服务端的 `ADMIN_REQUIRED` 上，不在导航上），
本条是把它细化，不该走回头路。

#### 账号匿名化删除：产品的决定，且有两个前置问题

V0.2 交付的注销是**停用式**（理由见 §4.1）：可逆、与「只停用不删除」一致、审计链
不断。面对个人信息删除诉求时它不够——那要求真正抹掉可识别信息。结构不必推倒，补
一条匿名化迁移即可，但**先要回答两件事，否则写出来的代码是白写**：

**① 审计日志里的主体怎么办。** 删行等于毁掉追溯链，而审计存在的意义正是事后能追。
通常的做法是把主体换成不可逆的假名而非删除记录——但那意味着「删除」不是字面意义
上的删除，这一点必须对提出诉求的一方讲明白，而不是留在实现里当作技术细节。

**② 目录再推一次同一个人怎么办。** [ldap.md](../ldap.md) 写得很明确：从目录里消失
的账号停用，**重新出现则重新启用**——那是「目录是事实源」的应有之义。于是一个被
匿名化的账号，只要它在 AD 里的条目还在，下一次同步就会把它复活，匿名化被静默撤销。
SCIM 侧同理，对账键是 `externalId`。所以要么匿名化时一并切断对账键并拒绝再次创建，
要么要求先从目录里删掉——这是产品要给的答案，实现替它定不了。
