# 生产环境部署

你要部署的东西是**一个二进制加一个 PostgreSQL**。控制台、手册和 API 是同一个
进程 —— 没有静态站点要托管，没有 worker 要调度，前面除了终结 TLS 的那一层之外
不需要再放别的。

这一页写的是 [访问指南](access-guide.zh.md) 里没有的那部分：编排系统需要知道
什么、跑多份的时候会发生什么，以及一次升级到底做了什么。

## 三个密钥

其余每一个环境变量都有能用的默认值。这三个没有，或者不该有。

| | 丢了会怎样 |
|---|---|
| `PORTICO_DB_DSN` | **起不来。** 不设置，服务器直说一句然后退出 —— 故意的，因为按默认值挑出来的数据库一定是错的那个。 |
| `PORTICO_JWT_SECRET` | **所有会话失效。** 它不阻止启动：不设置就**每个进程**自己随机生成一个，于是重启即掉线；跑多份的时候，一个实例签发的 token 会被其他实例拒绝。 |
| `PORTICO_ENCRYPTION_KEY` | 目录的 bind password、webhook 自定义头、外部提供方的 client secret 全都变成读不出来的密文。**行还在，行里的东西没了。** |

后两个**不在数据库里**，所以 **`pg_dump` 不等于这个系统的备份**。
[备份与恢复](backup-and-restore.zh.md) 写了还要复制什么，以及少了哪一样、在你
真的要用这份备份的时候会付出什么代价。

## 存活探针与就绪探针

```
GET /api/v1/health   → 永远 200，不依赖任何东西
GET /api/v1/ready    → 200，数据库连不上时 503 NOT_READY
```

**存活（liveness）指向 `/health`，就绪（readiness）指向 `/ready`，不要反过来。**
理由写在处理函数里，这里值得重复一遍，因为**弄反了就是把一个难受的下午变成一次
故障**：

- 存活问的是「**这个进程是不是坏了、要不要重启它**」。数据库挂了不是靠重启每个
  实例来修的，而这么做会在它最扛不住的时刻，把一个依赖故障变成整个集群的重启
  风暴。
- 就绪问的是「**要不要把流量发到这里**」。同一次故障里，这个问题的答案是不要。

所以 `/health` 是刻意不带任何依赖检查的。以后真要加依赖检查，加在 `/ready`。

容器镜像里没有 shell 也没有 `curl`，所以它自带的 `HEALTHCHECK` 跑的是
`portico ready` —— 这个子命令存在的理由就是这个。你也可以直接用，它接受
`--addr`。

## 关停

`SIGINT` 和 `SIGTERM` 会启动优雅关停：监听端口先关，在途请求有 **15 秒**完成。
给编排系统配一个**大于 15 秒**的 `terminationGracePeriodSeconds`，否则它会
`SIGKILL` 掉一个本来能干净退出的进程。

## 多实例部署

三个后台任务里有两个本来就是照多实例设计的。有一样不是，另有一样只在某一个时刻
需要留神。

### 安全配置项

**Webhook 投递**和**目录同步**都用 `FOR UPDATE SKIP LOCKED` 认领任务。两个实例
在同一分钟碰到同一个到期的目录，正是这条查询当初写出来要处理的情况：第二个会拿
到另一行，或者什么也拿不到。**不会因为多了一个副本就投递两次、或者同步跑两遍。**

**会话**是用 `PORTICO_JWT_SECRET` 签名的 JWT。任何实例都能验证任何 token，所以
不需要会话粘连、不需要共享会话存储、没有东西要复制 —— **前提是每个实例拿的是
同一个密钥**，也就是上面那张表里点名的那种翻车方式。

### 注意事项

**登录限流是按进程计数的。** 它是内存里的一个 map，所以三个副本就是三份独立的
额度，实际放行量是配置值的三倍。

**这不是一个要绕过去的缺陷，这就是这个限流器的定位。**
[访问指南](access-guide.zh.md) 里已经把话说明白了：Portico 只提供明文 HTTP，
限流交给反向代理。内置的这个是**下限** —— 让单实例不至于毫无防护，而**不是**你
应对撞库的答案。真正的限流要设在请求本来就被集中计数的那一层，然后盯着
`portico_sign_in_attempts_total{outcome="bad_credentials"}`，它会告诉你那个限制
是不是该收紧了。

### 数据库迁移

**每个实例启动时都会执行待应用的迁移，而且没有加锁。** 所以几个实例同时对着一个
需要迁移的数据库启动时，它们会赛跑。

结果具体是什么样，值得如实写出来，因为它比听上去要好：**一个赢了，正常启动；其余
的以非零码退出**，报一个迁移错误（`goose_db_version` 不存在，或者某个关系重复），
然后被编排系统重启 —— 那时赢的那个已经做完了，它们就正常起来了。**不会出现做了
一半的迁移**：本仓库每一条迁移都在事务里，没有任何一条带 `NO TRANSACTION`。

所以多副本滚动升级的代价是**日志里的一点噪音和几次重启，不是一个坏掉的 schema**。
如果你连这点噪音也不想要：

1. **缩到 1 个副本**，让它迁移完，再扩回去。最简单，代价是一小段容量下降而不是
   停服。
2. **让一个实例先跑** —— init container，或者一个 Job —— 等它就绪之后再起其余的。

无论走哪条，**升级前先读发布说明里有没有新迁移**：新旧实例同时在跑的那个窗口，
是两边都在对着新 schema 说话的窗口。

### 连接池配置

每个实例**最多开 25 个**连接，保持 5 个空闲。PostgreSQL 默认
`max_connections = 100`，而且通常已经有别的东西占掉了一些。

```
4 个实例 × 25 = 100    ← 正好顶到默认上限，还没算别人
```

**超过 3 个副本就要调大 `max_connections`**，或者前面放一个 PgBouncer。它翻车
不在启动的时候 —— 是在有负载的时候报连接错误，而那种错误比启动失败难认得多。

## TLS

Portico 只提供明文 HTTP，指望前面有东西。把 `PORTICO_PUBLIC_URL` 设成**人们真正
访问的那个地址**：OpenID Connect 的 discovery 拿它对外宣告、SAML 元数据里带的是
它、外部身份提供方的回调地址也是用它拼出来的 —— 这几样都要和另一个系统那边登记
的值**逐字符一致**。

[访问指南](access-guide.zh.md) 里有一份写好的 nginx 配置，包含这一页刚刚推给它的
那个限流。

## 指标

默认不开。`PORTICO_METRICS_ADDR=:9090` 会另开一个监听，只服务 `/metrics`，别的
什么都没有 —— 单独一个端口，这样抓取就不必穿过 API 的鉴权，而且**在内网暴露指标
不等于对公网暴露**。

值得配告警的是哪几条，见 [访问指南](access-guide.zh.md)。

## 资源规模

这个二进制是单个 Go 进程，控制台和手册都编译在里面；它不持有缓存，也不持有队列。
实际的内存下限是几十 MB，推高它的是**并发量，不是租户有多大**。

唯一值得知道的 CPU 开销是**密码哈希**，而且那是故意的：**登录本来就是这个系统里
昂贵的那条路。** 一波登录才是让这个进程干活的东西，而它早在被 Pod 限住之前，就已
经被限流器和你的代理限住了。

先给 256Mi 和 500m，观察，再调。**比这更具体的数字，以这个项目现在的年纪，是编出
来的而不是量出来的。**

## Kubernetes

`deploy/k8s/` 下有一个 Deployment、一个 Service 和一份 Secret 示例。它们是**起点，
不是 chart**：探针、grace period 和环境变量这几处最容易配错，而它们在那里已经是
对的了。

它们**通过了 schema 校验，但从来没有被 apply 到任何集群上** —— 这个项目没有集群
可以 apply。用之前先读一遍。
