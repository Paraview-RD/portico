# Go Code Conventions

Standard Go practice applies — `gofmt`, [Effective Go], and the
[Go Code Review Comments] are assumed and not repeated here. This document
covers the decisions specific to this codebase: where code goes, which
direction dependencies run, and the few patterns worth being consistent
about.

[Effective Go]: https://go.dev/doc/effective_go
[Go Code Review Comments]: https://go.dev/wiki/CodeReviewComments

## Package layout

```
cmd/server/        process entry point: flags, logging setup, signals
internal/
  config/          environment parsing; no dependencies
  model/           domain types shared across layers; no dependencies
  httpx/           HTTP plumbing: envelope, errors, middleware
  store/           database access; sqlcgen/ is generated
  auth/            passwords, tokens, authentication middleware
  notify/          message delivery: SMTP, and an SMS interface
  service/         business rules
  oidcp/           the OpenID Provider adapter
  samlp/           the SAML identity provider adapter
  casp/            the CAS protocol
  provision/       a second composition root, for the operations with no
                   HTTP surface: tenants, clients, service providers
  handler/         HTTP handlers
  server/          wiring: builds everything and mounts routes
  web/             embeds the built frontend
migrations/        schema, embedded
```

The three protocol packages sit **beside** the API rather than inside it.
Each answers the questions its protocol asks about accounts, clients, and
keys, and each is driven by that protocol's own router rather than by
`handler`. They may reach `service` and `store`; they must not reach
`handler`, `httpx`, or `server` — an endpoint one of them needed from there
would mean the protocol was leaking into Portico's own API surface rather
than sitting alongside it.

Each has exactly one seam back into the API: an authenticated endpoint the
sign-in screen calls to say who is at the keyboard, since a protocol
endpoint reached by a plain browser navigation carries no credential this
application can read.

Packages are named for **what they are**, not what kind of thing they
contain. There is no `utils`, `common`, or `helpers` package — those
accumulate unrelated code because nothing is ever obviously out of place in
them. If something has no home, that usually means a package is missing.

## Dependency direction

Dependencies run one way, and the compiler enforces it (Go rejects import
cycles outright):

```
handler ──→ service ──→ store
   │           │
   └──→ auth ──┘
        │
        ├──→ httpx
        └──→ model

model, httpx, config: no project dependencies at all
store: only its own subpackages (sqlcgen) and migrations
oidcp, samlp, casp: service, store, auth, model — never the web stack
```

The rules that matter:

- **A handler must not reach the store.** Everything goes through a
  service. A handler that queries directly is how business rules end up
  duplicated across endpoints and enforced in some but not others.
- **A service must not import `handler`.** If a service seems to need
  something from the HTTP layer, that thing belongs in `model` or is a
  parameter.
- **`model` and `httpx` depend on nothing else in the project**, and
  `store` depends only on its own subpackages and the embedded
  `migrations`. They are the leaves; keeping them that way is what makes
  them testable in isolation and is why a change to business rules cannot
  ripple into them.

These are the rules `internal/server/layering_test.go` enforces. It reads
its own table, so this document and that test can drift apart in one
direction: a package added there and not here. If you add one, add it in
both.

`service` importing `auth` is deliberate: authentication is a domain
concept here (who the actor is, whether their session is still valid), not
a transport detail.

## Layers

**`handler`** parses and validates the wire format, calls one service, and
renders the result. No business rules. A handler that is more than about
thirty lines is usually doing something a service should.

**`service`** owns the rules — what makes a request legal, what the
consequences are, what gets audited. It knows nothing about HTTP beyond
returning typed errors that carry a status, which
[error-conventions.md](error-conventions.md) explains.

**`store`** executes queries and nothing else. No business decisions live in
SQL. Most queries are generated by sqlc from
`internal/store/queries/`; see
[database-conventions.md](database-conventions.md).

**Storage types never reach the API boundary.** `sqlcgen.User` is a row —
it carries the password hash and the token version. `model.User` is what
the API returns. The conversion is explicit, in the service layer, so
adding a column cannot silently publish it.

## Construction and dependencies

- **Dependencies are constructor arguments**, held in unexported struct
  fields. No package-level singletons, no service locator, no init-time
  registration. `server.New` is the one place the graph is assembled, so
  the whole wiring of the program is readable in one function.
- **Constructors are `NewThing`** and return a concrete type, not an
  interface. Let the caller decide whether it needs an abstraction.
- **Interfaces are declared where they are consumed, not where they are
  implemented.** `auth.UserLookup` is defined in `auth` because that is
  what needs it; `service.UserService` satisfies it without importing
  anything to do so. This is why `auth` does not depend on `service`.
- **There is exactly one hand-written interface in the codebase**
  (`auth.UserLookup`), and that is the right number so far. Do not add one
  until there is a second implementation, or a test that genuinely cannot
  be written without it. A one-implementation interface is indirection with
  no payoff, and it makes navigation worse — "go to definition" lands on a
  method signature instead of the code.

## Mutable state

There is almost none, and that is intentional. Two package-level variables
exist:

- `web.embedded` — the embedded filesystem, immutable.
- `httpx.trustProxyHeaders` — set once at startup from configuration,
  read-only afterwards.

Anything else that wants to be package-level state should be a struct field
instead. Global mutable state makes tests order-dependent, which is a
failure mode that shows up as flakiness far from its cause.

## Context

Every service method takes `ctx context.Context` as its first parameter and
passes it down to the query layer, so a cancelled request stops doing work.
Never store a context in a struct, and never pass `nil` — use
`context.Background()` where there genuinely is no request.

## Errors

Covered in [error-conventions.md](error-conventions.md). The short version:
wrap with `%w`, never swallow, construct typed errors where the rule lives,
render once at the boundary.

## Naming

- Exported identifiers have doc comments beginning with the name. The linter
  enforces this.
- No stutter: `auth.Account`, not `auth.AuthUser`. Read names as the caller
  writes them.
- Acronyms keep their case: `ID`, `URL`, `HTTP`, `IP` — `userID`, not
  `userId`.
- Receivers are one or two letters and consistent across a type's methods.

## Tests

- **External test packages** (`package auth_test`, not `package auth`).
  This forces tests through the exported API, so a test cannot depend on an
  internal detail and quietly prevent a refactor.
- **Table tests for input variations**, with a `name` field. Each case is a
  `t.Run` subtest so a failure names itself.
- **Failure messages say what was expected and what happened**:
  `t.Errorf("status = %d, want 403", got)`. "assertion failed" costs the
  reader a trip to the source.
- **Comment the non-obvious cases with why they exist.** A test asserting
  that a disabled account is rejected immediately should say that it is
  about revocation taking effect before expiry — otherwise a future reader
  cannot tell whether it is load-bearing or incidental.
- **End-to-end tests go in `internal/server`**, driving the real router,
  services, and a temporary database. That is where the layers are proven to
  fit together; unit tests below it cover the branches.
- **Coverage is measured with `-coverpkg=./...`**. The default per-package
  number is misleading here, because the end-to-end tests exercise handler
  and service code from a different package and Go does not attribute that
  by default.

## Comments

Comments explain **why**, not what. The code says what it does; a comment
that restates it goes stale and adds nothing.

Worth a comment: a decision that looks wrong without context, a workaround
for someone else's behaviour, an ordering that matters, a rule that comes
from the requirements rather than from the code. The password-change flow
ending the session, the deliberate constant-time comparison on unknown
usernames, and Vite's output directory being the Go package are all
examples — each would otherwise look like a mistake.
