# SCIM 目录供给

Portico 支持 SCIM 2.0（RFC 7643、RFC 7644），因此一个目录——Okta、Entra ID，或
任何讲这个协议的系统——可以创建、更新、停用账号，而不需要任何人把它们再录入一遍。

基础地址：`https://<host>/scim/v2`

## 实现范围

这是配置任何东西之前最值得读的一节。**一个声称的能力多于实际实现的 SCIM 服务端，
会产生一次"半通"的推送**，所以这里的发现端点刻意如实——这样你的身份提供方在自己
的配置界面上看到的就是真相。

| | |
|---|---|
| **Users** | 创建、读取、替换、PATCH、停用、过滤 |
| **Groups** | 创建、读取、替换、PATCH、删除、过滤，以及完整的成员管理 |
| PATCH | Users：`active`、`userName`、`displayName`、`externalId`、`emails`、`phoneNumbers`。Groups：`members`、`displayName`、`externalId` |
| 属性 | core User 模式的 `name` 各分段、`nickName`、`profileUrl`、`title`、`userType`、`preferredLanguage`、`locale`、`timezone`、`photos`、`addresses`；以及 enterprise 扩展的 `employeeNumber`、`costCenter`、`department`。POST、PUT、GET 都携带 |
| 过滤 | Users：`userName eq "..."`、`externalId eq "..."`。Groups：`displayName eq "..."`、`externalId eq "..."` |
| Bulk | 不支持 |
| 排序 | 不支持 |
| ETag | 不支持 |
| changePassword | 不支持——密码不能经 SCIM 设置 |

`GET /scim/v2/ServiceProviderConfig` 返回同一份清单，并且**有测试断言两者一致**：
声明了的每一项能力都有能用的处理逻辑，没有声明的也不会偷偷生效。

### 属性同步范围

上面那些描述性属性按 RFC 7643 给出的名字存储，这正是目录推过来的字段能落到正确位置
的原因——而不是落进这个项目自己发明的什么东西里。

有两样东西是它们**刻意到不了**的：

**`manager` 不从 SCIM 读取。** 它按 id 指向另一个账号，而目录的 id 空间是它自己的
——接受它要么意味着存一个外部标识符，要么意味着同步时还得去解析它。请在控制台里
设置；Portico 会在 GET 时报告它，所以目录可以读回运维人员的选择。

**`organization` 与 `division` 被忽略。** Portico 有一棵组织树，树上的编码会被下游
系统保存。在它旁边再放一份自由文本的副本必然漂移，而两者不一致时没人说得清该信哪
一个。enterprise 扩展的 `department` **是**保留的，作为自由文本——**恰恰因为**它
经常写的是这个租户的树里没有的东西，丢掉它就丢掉了运维人员本可以据此行动的信息。

上面那一行属性，是 POST 与 PUT 接受的集合，也正是 `/Schemas` 公布的集合——一个读那份
文档的目录，能找到其中的每一个。PATCH 那一行刻意更短，原因见下一段。

**PUT 是替换，PATCH 不是。** SCIM 的 PUT 意思是"这个资源现在就是这样"，所以一个
不再发送 title 的目录是在说 title 没有了，Portico 会清空它。如果那不是你想要的，
就用 PATCH——这也是上面 PATCH 那一行列出的集合更短的原因：那些是**有处理逻辑**的
路径。

**这个集合是发现不到的。** `ServiceProviderConfig` 只说 `patch: supported`，而 SCIM
没给它任何一个字段去说明是哪些路径——所以这份清单唯一的机器可读形式，是客户端试一个
之后收到的那个 `invalidPath` 错误：它会点名那个属性，并把其余的列出来。

### 用户组不是组织

Portico 两者都有，而它们是不同的东西：

| | 组织 | 用户组 |
|---|---|---|
| 每人几个 | 恰好一个 | 任意多个 |
| …外加挂靠 | 任意多个，仅供参考：不授予任何权限、不参与同步、不改变上面那一个 | — |
| 形状 | 一棵树 | 扁平 |
| 靠什么标识 | 一个下游系统会保存的稳定编码 | 它的名字 |
| 通常由谁维护 | 管理员 | 目录 |

SCIM 的 Groups 映射到**用户组**。它们刻意不碰组织：组成员关系是多对多的，硬把它塞
进单值的组织字段，**要么会破坏下游系统所依赖的组织架构，要么会在目录第一次把某人
加进第二个组时静默地改掉他的组织**。

所以一次组推送只做它字面上说的事，别的什么都不改。如果你还希望由目录来决定人在
组织架构里的位置，那是另一个功能，这个不是它。

**成员身份不授予任何权限。** 这里只有两个固定角色、没有 RBAC，所以没有任何东西可
供一个组去承载——而如果这一点将来改变，它会是被刻意改变的，不会是因为某个目录写了
一个属性。

### DELETE 操作的行为

`DELETE /Users/{id}` 是**停用**账号，而不是删掉那一行。Portico 只停用、从不删除，
这样审计轨迹指向的始终是一个存在的东西——**一条指向已消失 id 的记录，事后回答不了
任何问题**。

之后这个账号仍然可读，`active: false`。这对你的同步很重要：**一个把 404 当作"没了"
的客户端，会在下一次执行时重新创建这个账号。**

`DELETE` 与 `PATCH active=false` 走同一条代码路径，所以取消供给不可能一种方式有效
而另一种无效。

## 配置步骤

### 1. 签发一份凭据

控制台里 **目录供给 → 新建凭据**，或者：

```bash
curl -X POST https://<host>/api/v1/scim-credentials \
  -H "Authorization: Bearer <admin token>" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Okta production"}'
```

响应里包含令牌。**它只显示一次。** 存下来的是一个 SHA-256 摘要——这正是"一份数据库
导出不等于一套可用凭据"的原因，同时也意味着**任何人（包括你）事后都无法还原它**。
丢了？再签发一个，把旧的删掉。

一份凭据的作用域限定在 `/scim/v2` 和一个租户内。它**不能**登录控制台、**不能**读取
API，背后也**没有**任何账号。

### 2. 让你的目录指向它

| 配置项 | 值 |
|---|---|
| SCIM 基础地址 | `https://<host>/scim/v2` |
| 认证方式 | HTTP Header / OAuth Bearer Token |
| 令牌 | 上一步签发的那个 |
| 供给内容 | 用户与用户组——创建、更新、停用，以及组成员关系 |

### 3. 验一下

```bash
curl https://<host>/scim/v2/ServiceProviderConfig \
  -H "Authorization: Bearer <scim token>"
```

## 组成员关系

目录实际会执行的是 `PATCH /Groups/{id}`，下面这些形态**全部**能识别，因为不同的
提供方发的不一样：

```jsonc
// 添加
{"op":"add","path":"members","value":[{"value":"<userId>"}]}

// 移除——id 在 path 里，这是 Okta 发的形态
{"op":"remove","path":"members[value eq \"<userId>\"]"}

// 移除——id 在 value 里
{"op":"remove","path":"members","value":[{"value":"<userId>"}]}

// 替换：现在整个成员集合就是这些，这是 Entra 的对账方式
{"op":"replace","path":"members","value":[{"value":"<userId>"}]}
```

`PUT /Groups/{id}` 同样会替换成员集合，因为 PUT 替换的是整个资源，而成员是它的一
部分。

**成员里出现不存在的账号会让整个请求失败**，返回 400 和 `scimType: invalidValue`。
它不会被跳过：**一个被静默丢掉的成员会留下一个看起来已同步、实际没有的组，而这恰
恰是你的目录从它那一侧检测不到的那种失败。**

`GET /Users/{id}` 会报告一个账号所属的组，这样客户端可以读回自己的推送是否落地。
那个字段是**只读**的——成员关系通过 Group 资源修改，所以只有一种改法，也就不存在
"哪一边说了算"的问题。

## 目录的权限边界

它可以设置：`userName`、`displayName`、`emails`、`phoneNumbers`、`externalId`、
`active`。

它**不可以**设置角色或组织，而这是**边界**，不是遗漏。SCIM 里没有 Portico 这两个
角色的概念，所以任何映射都得是发明出来的——而**一个发明出来的映射，就是一条"靠写
目录属性把自己变成管理员"的路**。目录说这个人是谁；Portico 说这个人能做什么。

它不可以设置密码。目录推密码意味着它持有一个可以重放的值，而且本部署自己的策略
——长度、历史、有效期——会作用在一个这里没人选过的东西上。

## externalId 的作用

给你供给的每一个账号绑定 `externalId`。它是**唯一稳定的对账键**：用户名和邮箱地址
恰恰是同步最可能正在修改的那些属性。

Portico 按它对账。`POST /Users` 时如果 `externalId` 已存在，**更新那个账号**而不是
再建一个——**包括 `userName` 已经变了的情况**，而那正是有人在目录里被改名时发生的
事。没有它，一次匹配不到既有账号的供给执行就会创建一个新的，**而这是 SCIM 集成
"测试通过、上线后把目录复制了一份"最常见的方式**。

## 停用效果

在一次操作里立即完成：

- 账号被停用，之后每一个请求都被拒绝；
- 它持有的每一个会话被吊销，打开着的浏览器随即失效；
- 每一个联邦刷新令牌（refresh token）被吊销，它登录过的应用无法再刷新。

唯一做不到的是伸进一个**自己维护会话**的应用里——**没有任何身份提供方能做到**。见
[单点登录](federation.md#各协议的吊销范围)。

**目录无法停用最后一个在用的管理员。** 这个请求会被拒绝而不是被执行：目录不再列出
某个人是一件寻常的事，而没有这道护栏，一个离职者的最后一天会把所有人锁在这个租
户外面。

## 错误

用 SCIM 自己的形态，而不是 Portico 的信封，这样你的目录能把它报出来：

```json
{
  "schemas": ["urn:ietf:params:scim:api:messages:2.0:Error"],
  "scimType": "invalidPath",
  "detail": "This server does not support patching title. Supported paths: ...",
  "status": "400"
}
```

对一个本服务端不存储的属性做 `PATCH`，回的是 **400 加 `scimType: invalidPath`**，
并点名那个属性——**不是 501**。这个区别在你真正会读到它的地方才显出意义：同步日志
里的一个 501 说的是"服务器坏了"，而这个说的是"哪一个属性谁都设不了"。

`PATCH` 是全有或全无。如果第三个操作不被支持，前两个也不会被应用——收到错误的客户
端会重试整个请求体，而**一个被部分应用的 patch 是一种两边都不知道的状态**。

## 审计

目录供给有它自己的审计动作——`SCIM_USER_CREATE`、`SCIM_USER_UPDATE`、
`SCIM_USER_DISABLE`、`SCIM_USER_ENABLE`——与管理员操作产生的那些分开。对事后读这条
轨迹的人来说，**一次自动的取消供给和某个人决定停用一位同事，是两件不同的事**。

签发和吊销凭据的审计权重与注册一个应用相同：**这样一份凭据可以在没有人在场的情况下
改变这个租户里的每一个账号。**

凭据列表会显示每一份最后一次被使用的时间，而这正是"目录悄悄不同步了"时人们会问的
那个问题。
