# Database Conventions

How schema and migrations are written in this project. Like
[api-conventions.md](api-conventions.md) and
[design-principles.md](design-principles.md), these are written from general
practice for this codebase — they describe what the schema in
[`migrations/`](../migrations/) actually does, so a reviewer can check code
against them.

The current schema is small (four tables). These conventions exist so it
stays coherent as it grows, not because it is complicated today.

## Naming

- **Tables** are plural, `snake_case`: `users`, `organizations`,
  `audit_logs`, `system_settings`.
- **Columns** are `snake_case`. Foreign keys end in `_id`
  (`organization_id`); enumerations are named for what they hold
  (`status`, `role`, `kind`, `source`, `result`).
- **Indexes** are prefixed by what they are: `idx_` for a plain index,
  followed by the table and the columns —
  `idx_audit_logs_kind_created`. A reader should be able to tell what an
  index covers without opening the schema.
- Names spell words out. `organization_id`, not `org_id`.

## Columns

- **Every table has `id TEXT PRIMARY KEY`**, holding a UUID generated by the
  application, not the database. Application-generated ids mean a record can
  be referenced before it is written, and they carry no information — an
  auto-incrementing integer leaks how many accounts exist and how fast they
  are being created, which for an IAM is a real disclosure.
- **The primary key is never updated.** Nothing else is a stable handle.
- **Columns are `NOT NULL` with a `DEFAULT`** unless absence genuinely means
  something. Today exactly one column is nullable — `users.organization_id`,
  where NULL means "belongs to no organization", which is different from any
  sentinel value that could be mistaken for a real id.
- **Never use a magic value to mean NULL.** No `0`, no `-1`, no `""` standing
  in for "unset". Empty string is used where empty string is a legitimate
  value (an unset phone number is genuinely the empty string, not an unknown
  one).
- **Timestamps are `created_at` / `updated_at`**, stored as ISO 8601 text in
  UTC. See [Timestamps](#timestamps) for why text.

## Types and constraints

- **Enumerations are `TEXT` with a `CHECK` constraint** listing every valid
  value:

  ```sql
  role TEXT NOT NULL DEFAULT 'USER' CHECK (role IN ('SUPER_ADMIN', 'USER'))
  ```

  Not a SQL `ENUM` type — those are hard to alter and behave differently
  across engines. The `CHECK` is a genuine backstop: it is what catches a
  service-layer bug that would otherwise write an invalid state, and the
  schema tests assert that it does.

- **Foreign keys are declared and enforced.** This is a deliberate departure
  from the common advice to avoid database-level foreign keys — that advice
  is about sharded, high-write deployments where the constraint is expensive
  and cannot span shards. Neither applies here, and the constraint has
  already caught a bug in a test.

- **Money, if it is ever stored, uses an exact decimal representation** —
  never a float. There is no money in the schema today; this is here so the
  first person to add some does not have to relitigate it.

## Timestamps

`TIMESTAMPTZ`, always. The driver scans it straight into a Go `time.Time`,
so there is no conversion layer and no format to agree on.

Everything is stored in UTC. Localization happens in the browser, from the
reader's own locale and zone — a server that formats dates has committed to
one of each for everybody.

An earlier version stored ISO 8601 text, because SQLite has no timestamp
type and something had to be picked. That shim is gone.

## Comments

Non-obvious columns carry a `COMMENT ON`, and the bar for "non-obvious" is
low — `token_version` and `users.source` both have one, because neither is
guessable from its name.

These are worth writing for a reason beyond documentation: sqlc lifts them
into doc comments on the generated Go structs, so an explanation written
once in the schema shows up wherever the field is used.

A column whose purpose cannot be explained in one line probably wants to be
two columns.

## Records are disabled, never deleted

There is no soft-delete timestamp and no `deleted` flag. Users and
organizations carry a `status` of `ACTIVE` or `DISABLED`, and nothing in the
application issues a `DELETE`.

This is a product requirement rather than a storage preference: the audit
trail references users, and deleting a row — even softly — would leave log
entries pointing at nothing. `status` also carries meaning that a deletion
flag cannot, since a disabled account can be re-enabled.

## Migrations

Migrations live in [`migrations/`](../migrations/), are embedded into the
binary, and run automatically at startup. There is no migration CLI to
install or run separately — deploying is still just running the binary.

- **Numbered sequentially**: `00001_init.sql`, `00002_....sql`. The number
  orders them; the description says what they do.
- **Never edit a migration that has been released.** Its checksum is
  recorded, and changing it breaks every existing deployment. Add a new one.
- **DDL should be idempotent where the tool does not already guarantee it**
  (`IF NOT EXISTS`), so a partially-applied migration can be re-run.
- **Every migration has a `-- +goose Down`** that actually reverses it. An
  irreversible migration is sometimes unavoidable, but it should be a
  decision, not an omission.
- **No triggers and no stored procedures.** Behavior belongs in the service
  layer where it is testable, reviewable in a diff, and visible to someone
  reading the Go code. A trigger is action at a distance.

### Changing a column that is in use

Do it in three steps across releases, never in one:

1. **Add** the new column, nullable or defaulted. Write to both.
2. **Migrate** the data, and switch reads to the new column.
3. **Remove** the old column, once no running version reads it.

Each step leaves the database compatible with both the previous and the
current release, which is what makes a rollback survivable. Collapsing them
into one migration means any rollback is a data-loss event.

## Queries

Most queries are generated from [`internal/store/queries/`](../internal/store/queries/)
by [sqlc](https://sqlc.dev), which type-checks them against the schema at
build time. Prefer adding one there over hand-writing SQL.

Hand-written SQL is appropriate when the shape of the query varies — the
user and audit-log list endpoints build their `WHERE` clause from whichever
filters were supplied, which sqlc cannot express. Those go through the
`filters` builder in `internal/service/common.go`, which numbers PostgreSQL
placeholders and accumulates arguments together, so the two cannot drift
apart. When you do write SQL by hand:

- **Every user-supplied value goes through a placeholder.** Never build SQL
  by concatenating a value, even one that "cannot" contain anything
  dangerous.
- **Only fixed string literals may be concatenated** into a statement —
  clause fragments chosen by the code, never data chosen by the caller.
- **`ORDER BY` and `LIMIT` are fixed**, never interpolated from input.
- **Escape `LIKE` wildcards** in user input and declare `ESCAPE`, or a search
  for `%` matches every row.
- **Placeholders are `$1`, `$2`, …**, numbered by position. Getting the
  numbering out of step with the argument slice binds values to the wrong
  conditions, which is why the builder exists rather than hand-counting.

## What is deliberately absent

- **Multi-tenancy is being added**, and it is a schema-wide change rather
  than a column — every table, every unique constraint, and every query.
  Until that lands, this section will be out of date the moment it does;
  see the requirements document.
- **No optimistic-locking `version` column.** Nothing in the current
  workload has concurrent-update contention worth the complexity.
  `users.token_version` is unrelated — it is a session revocation counter.
- **No partitioning, no sharding, no read replicas.** A single PostgreSQL
  instance is the assumption. Read replicas are a plausible later step; the
  connection pool would need to route by statement kind, which nothing does
  today.
